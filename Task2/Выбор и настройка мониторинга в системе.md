
## Мотивация

Есть очевидные проблемы системы с работоспособностью.
- Проблема с загрузкой MES сервиса
- Проблема с зависанием заказов
- Проблема с доставкой заказов к операторам
- Проблема с распределением заказов по операторам

На данный момент мы можем оценивать проблемы исходя из внешних признаков. 
Необходимо добавить в систему точки сбора **метрик-производительности** на которых можно было бы анализировать систему изнутри
Таким образом можно будет точнее определить узкие места и наблюдать динамику их исправления по ходу изменения ситемы 

Кроме того возможно настроить систему сбора **бизнес метрик**. 
Чтобы руководство компании могло анализировать бизнес значимость новой функциональности и влияния улучшения системы

## Выбор подхода к мониторингу

- На первом этапе мы предполагаем присутсвие очевидных проблем с производительностью системы.
Поэтому первоочередным считаю необходимость внедрения **USE** метрик.

Их предлагаю использовать для анализа работоспособности MES системы и связаных с ней сервисов

- Далее возможно внедрение метрик **четырех золотых сигналов**
С помощью них возможно будет проследить доработки связанные с добавлением систем кэширования, работоспособность пользовательских интерфейсов и конечных API

## План действий

Необходимо для сбора и отображения метрик настроить стек Prometheus + Grafana

под каждый набор метрик будет необходимо настроить соответсвующие экспортеры из соответсвующих компонентов


|Группа метрик|Источник данных|Инструменты|
|---|---|---|
|CPU/Memory Utilization|Серверы (Java Spring Boot, C#)|	Prometheus.NET, Micrometer + Prometheus|
|HTTP-запросы (RPS, Latency, 500 Errors)|Nginx/API|nginx-prometheus-exporter|
|RabbitMQ (Dead Letters, Queues)|RabbitMQ|rabbitmq-prometheus|
|S3 Storage Size|AWS S3/MinIO|aws-cloudwatch-exporter или аналог для конкретного S3|
|Трафик (Kb sent/received)|	Nginx|	nginx-prometheus-exporter|
|Simultaneous Sessions|Postgres|postgres_exporter|

## Дополнительное задание. Показатели насыщенности

например если говорить про показатель Size of S3 storage, то достаточно оповещения поддержки
Так как заполнение происходит относительно линейно. То вероятно необходимо будет завести тикеты на расширение хранилища

если говорить про Number of requests (RPS) per user for MES API, то опять же показатель скорее всего линейный и необходимо видеть рост и использовать метрику как визуальный показатель адекватности построения фронтов приложения.

Number of requests (RPS) for MES API  - если считаем рост штатным, то вероятно основываясь на нем необходимо настроить автоматическое масштабирование сервиса АПИ
