
## Общая информация о системе

Характеристики : 
 - Основа взаимодействия CRM -> MES. Через брокер rabbitMQ
 - Расчитывает стоимость MES. Время расчета от 2 до 30 мин 
 - у MES есть API
 - у MES есть UI. На первой странице отображается список заказов в работе по статусам — это дашборд с фильтром
 - заявленный срок изготовления - 3 недели

Факт 1: 
Производственные мощности позволяют увеличивать производство до х2

Факт 2:
Стандартное увеличение нагрузки - линейное. +100 заказов к предыдущему месяцу

Факт 3:
Задержки по несколько месяцев при стандартной работе

Факт 4:
После открытия апи у MES задержки ещё увеличились

Факт 5:
Жалоба от операторов. Первая страница MES долго прогружается.

Факт 6:
Операторам важно видеть самые новые заказы, 
потому что от этого зависит их вознаграждение, — кто взял заказ, тот и получит оплату.


## Анализ и идентификация проблем:

- Технические проблемы:
1. Явная проблема о которой заявлено. MES перегружен, UI тормозит
2. один экземпляр MES выполняет независимые операции: обработка моделей, бэкенд UI для операторов, обеспечение работы API
3. асинхронный обмен сообщениями через единственный экземпляр rabbitMQ. Навскидку rabbit должен справляться с задачами масштаба данной компании. но дополнительный анализ не помешает. Возможны проблемы с тем что MES не успевает их читать 

- Взаимодействие с MES и производство:
1. Проблема с логикой передачи заказов операторам. Операторы всегда видят и берут новые заказы. Если заказ не попал сразу к оператору, то он рискует быть всё время "в конце" списка и в работу его не возьмут
2. Несоответсвие фактов "Производственные мощности позволяют увеличивать производство" и заказы не успевают браться в работу и исполняться. Вероятная нехватка Операторов
       

## Предалгаемые решения:


1. Масштабирование MES 
- Так как MES является сторонним решением разбить его на миросервисы не представляется возможным.
Но возможно поднять несколько независимых экземпляров. Экземпляры разделить по логике функционала.

- В дальнейшем при росте нагрузки для каждого экземпляра также будет возможно создавать масштабируемые кластеры 
- Кроме этого в моменты низкой нагрузки можно будет использовать незагруженные экземпляры для ведения фоновых расчетов (например обработка 3d моделей)

Данное решение потребует дополнительно настройку gateway и балансировщика

2. Кэширование
- В данный момент система не кэширует данные вообще никак.
- Предалагается использовать как кэш на клиенте Интернет магазина (с установкой разумного времени хранения, например 1 день)
- Так и бэкенд систему кэширования как для MES API так и для shop API. Например хранение расчета цен на стандартные модели

3. Предварительный расчет цен на стандартные модели и хранение их в БД
- Возможно загружать MES экземпляры расчетом цен стандартных моделей во время низкой внешней нагрузки (например ночное время). Тем самым разгружая мощности в остальное время
- Уменьшение latency при запросах к API 

4. Изменение логики выдачи заказов операторам
- Текущая логика LIFO будет хорошо работать только в ситуации когда операторы готовы разбирать заказы быстрее чем они приходят. При нехватке операторов, в ситуации когда заказы приходят чаще, невзятый сразу заказ рискует быть невзятым в работу вообще.

Если есть какая-то бизнес необходимость использовать LIFO логику, то предлагаю сделать у MES UI что-то вроде системы backpressure. В моменты, когда много операторов работают и готовы брать заказы, использовать LIFO, при снижении активности операторов переключаться на FIFO и передавать им старые заказы, подвисшие в состоянии MANUFACTURING_APPROVED
